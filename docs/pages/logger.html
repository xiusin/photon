MDC 上下文
Mapped Diagnostic Context — 请求级追踪

MDC 允许在请求上下文中注入键值对，后续所有日志自动携带这些字段，非常适合请求追踪。

v
// 在中间件中注入 Request-ID log_.put('request_id', 'req-abc123') log_.put('user_id', '42') // 后续所有日志自动携带 request_id 和 user_id log_.info('Processing order') // {"ts":"...","level":"info","msg":"Processing order","request_id":"req-abc123","user_id":"42"} // 请求结束后清理 log_.remove('request_id') log_.remove('user_id') // Spring 等价：MDC.put("requestId", "req-abc123") // Go Zap 等价：logger.With(zap.String("request_id", "req-abc123"))

LogContext 上下文追踪
请求级结构化上下文 · trace_id / request_id 自动传播

LogContext — 请求级结构化日志上下文，提供 trace_id、request_id 等上下文字段的自动传播。灵感来自 Spring Sleuth 的追踪传播机制。

方法说明
new_log_context()创建空上下文
with_trace_id(id)设置 Trace ID（链式调用）
with_request_id(id)设置 Request ID（链式调用）
with_span(name)设置 Span 名称（链式调用）
with_field(key, value)添加自定义字段（链式调用）
to_fields()转换为 Map 供 Logger 使用
v
import photon.logger // 链式创建上下文 mut ctx := logger.new_log_context() .with_trace_id('trace-abc123') .with_request_id('req-456') .with_span('process_order') .with_field('user_id', '42') // 配合 Logger 使用 log_.with_fields(ctx.to_fields()) log_.info('Processing order') // Spring Sleuth 等价：MDC 中的 trace 传播 // Go 等价：context.Context with structured fields

MultiOutputLogger 多输出
同时输出到多个目标 · Console + File + Remote

MultiOutputLogger — 包装 Logger 并同时将输出发送到多个目标（如控制台 + 文件）。Spring 等价：Logback 的 Appender 链。

v
import photon.logger mut multi := logger.new_multi_output_logger(my_logger) multi.add_output(fn (msg string) { // 写入文件 os.write_file('app.log', msg + '\n') or {} }) multi.add_output(fn (msg string) { // 发送到远程 http_post('https://logs.example.com/ingest', msg) or {} }) // 所有日志同时输出到原始 Logger + 所有额外输出 multi.info('Server started') multi.error('Connection failed') // Spring 等价：Logback 的 Appender 链

Logger.add_sink() 通道输出
add_sink(Channel) — 将日志写入 FileChannel 等通道

Logger.add_sink() 允许将日志输出重定向到 Channel 实现（如 FileChannel），替代旧的 ChannelLogger 方案。sink 与 Logger 自身的输出独立工作，可同时写入控制台和文件。

v
import photon.logger mut log_ := logger.new() // 1. 添加 FileChannel sink — 日志同时输出到控制台和文件 log_.add_sink(logger.new_file_channel('/var/log/app.log')) // 2. 添加多个 sink（可叠加） log_.add_sink(logger.new_file_channel('/var/log/error.log')) log_.add_sink(logger.new_file_channel('/var/log/access.log')) // 3. 日志同时输出到 Console + 3 个文件 log_.info('Server started') // → stderr: encoder 输出（Console / JSON 视 encoder 而定） // → 每个文件: [ts] [INFO] [photon] Server started（敏感字段已脱敏） // 4. 按大小轮转（生产必备，避免日志写满磁盘） rot := logger.new_rolling_file_channel( filepath: '/var/log/app.log' max_size_bytes: 50 * 1024 * 1024 // 50MB 切一个文件 max_backups: 7 // 保留 app.log.1 .. app.log.7 ) log_.add_sink(rot) // 进程退出前 flush 并释放句柄 defer { rot.close() }

日志轮转（RollingPolicy）

字段说明
max_size_bytes单文件大小上限，<= 0 表示不轮转（默认）
max_backups保留的历史文件份数（.1 .. .N），默认 3；0 表示不保留历史、轮转时直接清空

轮转发生在写入前：即将写入的这一行会让文件超过上限时，先把当前文件改名为 .1（旧的 .1 顺延为 .2，依此类推），再写新文件 —— 单行日志不会被撕成两个文件。进程重启后按文件实际大小继续计数，不会把已有的大文件当成空文件。

外部工具（logrotate / systemd）接管轮转时，仍可调 reopen() 让通道重新打开同一个路径。

ChannelLogger 的状态

ChannelLogger 仍然完全可用，只是被列为「后续合并进 Logger.add_sink()」的候选。新代码建议直接用 add_sink(Channel)：sink 与 Logger 自身输出独立工作，多路输出更直观。注意 add_sink() 是 &Logger 上的 mut 方法，返回 void，不参与链式调用。

支持的 Channel 类型

Channel说明
StderrChannel写 stderr（默认通道，带脱敏）
FileChannel写指定文件，句柄常驻；可选按大小轮转 + 保留份数
SyslogChannelsyslog 通道（当前回落到 stderr）
自定义 Channel实现 Channel 接口即可：write(level Level, msg string, context map[string]string) + name() string
